# 第 8 章 从实验代码到工程结构

## 本章要解决什么问题

前七章一共写了 7 个脚本，每个都能单独跑。这是**故意**的 —— 第 1 章定下的规矩叫"每章自包含"，为的是你翻到任何一章都能直接运行，不用先搞懂前面六章。

但这个规矩是有代价的。把 7 个脚本摊开数一下**同一份代码被抄了几遍**：

| 函数 | 出现在几个章节脚本里 |
|---|---|
| `set_seed` | **8** |
| `get_device` | **8** |
| `evaluate` | **6** |
| `train_one_epoch` | **5** |

**一共 27 份副本。**

教学场景下这个代价是值得付的（换来"翻到哪章都能跑"）。但如果这是你的真实项目 —— 比如接下来要做 PoolNet —— 这个代价就付不起了：

- 改一处逻辑（比如给 `evaluate` 加上 Top-5 准确率），要记得去 6 个地方改
- 漏改一个地方**不会报错**，只会在某个实验里悄悄用旧逻辑
- 想加个新实验，第一件事是"复制一个脚本再改"，代码越滚越像

**本章要做的就是把这 27 份副本收成 1 份**，而且要做到一件比"能跑"更硬的事：

> **重构前和重构后的模型，权重必须一模一样。**

最后这句是本章的验收标准。8.7 节会看到它是怎么被验证的 —— 不是"看着差不多"，是**逐元素比对**。

## 8.1 五个文件，各管一件事

工程版放在 `code/ch08_project/`，五个文件：

```
code/ch08_project/
├── config.py     超参 + 路径            ← 唯一允许出现数字的地方
├── model.py      SimpleCNN             ← 网络长什么样
├── dataset.py    get_loaders           ← 数据从哪来
├── engine.py     训练/评估/checkpoint   ← 怎么训、怎么存
└── train.py      入口：把上面四个组装起来 ← 只有编排，没有实现
```

每个文件多少行：

| 文件 | 总行数 | 有效代码 |
|---|---|---|
| `engine.py` | 194 | 137 |
| `train.py` | 142 | 78 |
| `config.py` | 108 | 66 |
| `dataset.py` | 95 | 71 |
| `model.py` | 86 | 60 |

### 职责边界怎么划

判断一个文件该放什么，问一句话：**"换个场景，它会变吗？"**

| 文件 | 它的职责 | 什么情况下要改它 |
|---|---|---|
| `config.py` | 所有**能用数字表达**的可调项 | 换数据集、调超参 |
| `model.py` | 网络结构 | 换模型（比如换成 ResNet） |
| `dataset.py` | 数据读取与预处理 | 换数据集、改增强 |
| `engine.py` | 训练循环、评估、存取 | 换训练策略（比如加混合精度） |
| `train.py` | 把上面四样拼起来跑一次 | 基本不用改 |

最后一行是关键。`train.py` **应该是最不需要改的那个文件** —— 它是"编排"，不是"实现"。换个模型、换个数据集，入口的命令行和流程一个字都不用动。

<blockquote class="tip">

**💡 一个判断文件该不该拆的标准**

不要问"这个文件能不能再拆细"，要问 **"这两部分职责混在一起了吗"**。

本章把 `set_seed` / `get_device` 放进了 `engine.py`，严格说它们既不是"引擎"也不是别的什么，应该单独有个 `utils.py`。但这两个函数加起来 20 行 —— **为了 20 行多开一个文件，是另一种浪费。**

**文件拆分的成本是"读代码的人要多跳一次"，收益是"职责不混"。** 只有当收益大于成本时才拆。一个 600 行的文件里塞了 5 件事该拆；5 个 10 行的文件各自干一件事，很可能还不如合成一个。

</blockquote>

## 8.2 依赖方向必须单向

五个文件之间有明确的调用关系：

```
                    train.py                    ← 入口，谁都依赖它
                   ╱    │    ╲
            engine.py  model.py  dataset.py     ← 实现层
                   ╲    │    ╱
                    config.py                   ← 谁都依赖它，它不依赖任何人
```

三条规矩：

**① 箭头只能向下，不能向上。** `config.py` 绝不 import `train.py` —— 它压根不知道有谁在用它。

**② 不许有环。** 如果 `model.py` import `dataset.py`，而 `dataset.py` 又 import `model.py`，Python 会在导入时报循环依赖错误（或者更糟：在你没注意的地方拿到一个半成品模块）。

**③ `train.py` 可以 import 所有人，但**没有人 import `train.py`。** 这是"入口"的定义。

### 这条规矩落地成了一个可见的结果

回头看书里的 `config.py`：

```python
ROOT = Path(__file__).resolve().parent.parent.parent
```

**这是整个工程版里唯一一处 `__file__`。** 打开 `model.py` / `dataset.py` / `engine.py`，一次都看不到它 —— 它们要路径就 `from config import ...`。

<blockquote class="warn">

**⚠️ 踩到的坑：`parent` 要写三层，而且只能写一处**

第 1~7 章的脚本都在 `code/` 下，所以是两层：

```python
ROOT = Path(__file__).resolve().parent.parent      # code/ch01_data.py -> 仓库根
```

工程版**深了一层**（`code/ch08_project/config.py`），所以必须三层：

```python
ROOT = Path(__file__).resolve().parent.parent.parent
```

初版写完我先跑了一次 —— 数据能读到、checkpoint 也存对了，因为我把三层写在了唯一的那个文件里。

**但这里真正要防的不是"写错层数"，是"有第二个人也要数层数"。** 如果 `dataset.py` 里也写一遍 `parent.parent`，那它就是**错的**（`code/ch08_project/dataset.py` 的两层是 `code/ch08_project` 的上一层 = `code`，不是仓库根）——而且它错得**不报错**，只会去 `code/data` 找数据、找不到就重新下载一份到那儿。

**所以规矩是：路径只在一个地方算，别的文件一律 import。** 想验证，在 `dataset.py` 里搜一下 `__file__` —— 搜不到就对了。

</blockquote>

## 8.3 同一份逻辑，两种写法

这是本章最值得看的一节。前七章的代码和工程版不是"对与错"的关系，**是同一个逻辑服务两个不同目的**。逐项对比：

### ① 参数传递：散装的 vs 打包的

```python
# 第 1 章（教学）
def get_loaders(batch_size: int, limit: int = 0, seed: int = 42):
    ...

get_loaders(128, 0, 42)

# 第 8 章（工程）
def get_loaders(cfg):
    ...

get_loaders(cfg)
```

三个参数，教学版更好读：函数要什么，签名上一眼看得全，不用去翻 `Config` 的定义。**代价**是以后加参数要改所有调用点。

一旦参数长到七八个、调用点超过两三处，工程版开始赢 —— 加参数只改 `Config` 一行，调用点一个字不动。工程版 `Config` 现在有 8 个字段，正是这个区间。

### ② 默认值：写两遍 vs 写一遍

```python
# 第 5 章（教学）
CANONICAL_LR = 0.01
...
p.add_argument("--lr", type=float, default=CANONICAL_LR)
```

第 5 章这个写法**已经把默认值的来源收敛成一处**了 —— `CANONICAL_LR` 是唯一定义 `0.01` 的地方，`add_argument` 只是引用它。这一点第 5 章做得对。

```python
# 第 8 章（工程）：默认值从 Config 的默认实例上取，不写字面量
def parse_args():
    d = Config()                                        # 先拿一份默认配置
    p.add_argument("--lr", type=float, default=d.lr)    # 引用，不是字面量
    p.add_argument("--epochs", type=int, default=d.epochs)
    ...
```

**这里要老实说一句：这一条不是"工程版比教学版好"，而是"初版写漏了、后来补上"。**

工程版的第一版 `parse_args` 里写的是字面量 —— `default=10`、`default=0.01` —— 而 `Config` 里又各写了一遍。也就是说**同一批默认值有两个副本**，改一处忘另一处就静默不一致。

**它比第 5 章还差**：第 5 章引用了常量，反而是单一来源。

改成 `default=d.epochs` 之后就一致了。**所以别把"凡是工程版的写法"都当成更优的** —— 结构化的代码不会自动变对，它只是让"哪里该放什么"更清楚，具体的写法仍然要一条一条看。

### ③ 教学用的岔路，工程里要砍掉

```python
# 第 3 章（教学）：4 种初始化都留着，为了演示"方差有多重要"
class SimpleCNN(nn.Module):
    def __init__(self, init_mode: str = "kaiming"):
        if init_mode not in INIT_MODES:
            raise ValueError(...)
        ...

# 第 8 章（工程）：只留结论
class SimpleCNN(nn.Module):
    def __init__(self):
        ...
        self._init_weights()      # 里面只有 kaiming，没有分支
```

第 3 章留着 `init_mode` 是为了让你**亲眼看到** `zeros` 学不动、`large` 训不起来。演示完了，结论是"用 kaiming"。

工程代码里留着一个永远只传一个值的参数，等于给每个读代码的人加一次"我该传什么"的思考 —— 而正确答案只有一个。

**教学的版本要保留所有岔路，工程的版本只保留结论。**

### ④ 评估用的损失函数：自己建 vs 传进来

```python
# 第 3 章（教学）：函数内部自己建一个
def evaluate(model, loader, device):
    criterion = nn.CrossEntropyLoss()
    ...

# 第 8 章（工程）：调用方传进来
def evaluate(model, loader, criterion, device):
    ...
```

工程版的理由：**全流程只应该有一个损失对象**。哪天要把 `CrossEntropyLoss` 换成带 `label_smoothing` 的版本，改一处就够了 —— 不会出现"训练用的是这个损失、评估用的是另一个损失"这种**不报错**的错配。

### ⑤ checkpoint 存什么

```python
# 第 5 章（教学）：在训练循环里内联写
if va_acc > best_val_acc:
    ...
    torch.save(model.state_dict(), save_to)

# 第 8 章（工程）：抽成两个函数，各有名字
save_checkpoint(model, cfg.checkpoint)
load_checkpoint(model, cfg.checkpoint, device)
```

抽出来之后，「存什么、怎么存、加载时注意什么」这三件事终于**有了一个地方可以写注释**，而不是散在 700 行的脚本中间。

## 8.4 实测：工程版跑出来的是同一个模型吗

重构最大的风险是**悄悄改变了行为**。改完能跑通、准确率看着也差不多 —— 但真的是同一个模型吗？

**"看着差不多"不算验收。** 本章的验收标准是逐元素比对权重。

### 真正的验收：逐元素比对

准确率对得上还不够 —— 两个不同的模型完全可能碰巧都跑出 98.62%。所以直接比权重：

```python
import torch
a = torch.load("results/best_cnn.pt",   map_location="cpu", weights_only=True)
b = torch.load("results/ch08_best.pt",  map_location="cpu", weights_only=True)
print("键名相同:", list(a) == list(b))
print("全部张量逐元素相等:", all(torch.equal(a[k], b[k]) for k in a))
```

实测结果：

```
键名相同: True
全部张量逐元素相等: True
张量个数: 8
```

**8 个张量，逐元素完全相等。** 注意 `torch.equal` 是**逐位**比较，不是"误差小于阈值" —— 这意味着重构没有引入任何数值差异，哪怕 1e-7 的漂移都没有。

<blockquote class="done">

**✅ 这就是"重构成功"的定义**

判断标准不是"能跑"、也不是"准确率差不多"，而是：

> **同一个种子、同一份数据，重构前和重构后产出的模型，权重逐位相同。**

做不到这一条，就不是重构，是**改模型** —— 那就要重新走一遍第五、六、七章的对比流程，因为所有结论都可能变了。

</blockquote>

<blockquote class="tip">

**💡 顺便验证了"可复现"这件事本身**

</blockquote>

## 8.5 踩到的坑：探测设备会把随机数流挪走

这是本章最值得记住的一个坑，因为它**不报错、不影响"能跑"、只让数字悄悄变掉**。

### 现象

工程版第一版跑出来是这样：

```
    1 |     0.3324   90.54% |    0.1049  96.76% |   4.2
    ...
  验证集最好 98.57%（第 10 轮） | 测试集 98.53%
```

**测试集 98.53%，不是 98.62%。** 差 0.09pp —— 比第 3 章那把 0.43pp 的尺子还小，凭数字判断的话很容易当成噪声放过去。

但把整条 val 曲线列出来，问题就露出来了：

| | 第 1 轮 train | 第 1 轮 val | 第 3 轮 val |
|---|---|---|---|
| 应该是（第 5 章） | 92.15% | 96.68% | 98.07% |
| 第一版实测 | **90.54%** | **96.76%** | **97.97%** |

**从第 1 轮起就不一样了。** 这不是随机波动（波动不会让每一轮都系统性偏掉），这是**起点变了** —— 模型初始化拿到的随机数不是同一批。

### 原因

`train.py` 第一版是这么写的：

```python
set_seed(cfg.seed)      # ← 先固定随机源
device = get_device()   # ← 再探测设备
```

而 `get_device()` 为了验证 CUDA 真的能算，会跑一次：

```python
y = torch.relu(conv(torch.randn(2, 1, 28, 28, device="cuda")))
#                    ^^^^^^^^^^^^^^^^^^^^^^^^ 这里！
```

**`torch.randn` 消耗全局随机数流。**

于是顺序变成了：`set_seed` 定下起点 → `get_device` 用掉一段随机数 → 后面 `kaiming_normal_` 初始化拿到的**不是起点**，而是往后挪了一段的位置。

**而 `SimpleCNN` 的权重是 kaiming 随机初始化的** —— 起点挪了，权重就全变了；权重变了，整条训练曲线就变了。

### 修法

```python
device = get_device()   # ← 先探测（会消耗随机数）
set_seed(cfg.seed)      # ← 再固定随机源（把消耗覆盖掉）
```

改完重跑，逐行对上了第 5 章：

```
    1 |     0.2945   92.15% |    0.1128  96.68% |   3.9     ← 与第 5 章完全一致
...
early stop @ep9（best 是 ep6，val 98.42%）
  验证集最好 98.42%（第 6 轮） | 测试集 98.62%
```

<blockquote class="warn">

**⚠️ 为什么第 5 章没踩到这个坑**

因为它**碰巧**躲过去了：`ch05_hyperparams.py` 的 `run_trial` 函数开头又调了一次 `set_seed`，把 `get_device` 那次消耗覆盖掉了。

**那是巧合，不是设计。** 第 5 章那行 `set_seed` 的本意是"每组配置都从同一个随机状态出发"，跟设备探测没有关系 —— 它挡住这个坑纯属顺手。

所以这条经验要按**规律**记，不要按"第 5 章那样写就行"记：

> **凡是在"该确定下来的流程"之前动过随机数流的东西，要么挪到 `set_seed` 前面，要么让它内部用独立的 generator（`torch.Generator().manual_seed(...)`）。**

`get_device()` 完全可以自己带一个 generator 从而不碰全局状态 —— 但那样反而是**更差的设计**：一个"探测设备"的函数不该操心随机数。让它随便用、把 `set_seed` 放在它后面，更简单也更好懂。

</blockquote>

### 这个坑的真正教训

**0.09pp 这个数字，如果只盯着它，会得出"这是噪声"的错误结论。** 是"从第 1 轮就对不上"这个**形状**暴露了它。

第 6 章 6.4 节那个 `−3.93%` 的假 gap 也是同一类问题：**数字看着合理，但和它应该有的形状不符。** 所以对比两组结果时，不要只比最后一个数 ——

> **把整条曲线并排看。形状不对，说明不是噪声，是有东西真的变了。**

## 8.6 交付：工程版比教学版多做的一件事

看上面那次运行的最后两行：

```
  验证集最好 98.42%（第 6 轮） | 测试集 98.62%（损失 0.0421）
```

而第 5 章的教学脚本打印的是：

```
early stop @ep9（best ep6 98.42%） best_val=98.42% test=98.80%
```

**教学版写 98.80%，工程版写 98.62%。** 谁的模型更好？都不是 —— **它们评的根本不是同一个东西。**

原因在这里：

```python
# 第 5 章：训练跑完，模型里装的是「最后一轮」的权重
te_loss, te_acc = evaluate(model, test_loader, device)     # -> 98.80%

# 第 8 章：先把 best checkpoint 装回去，再评
load_checkpoint(model, cfg.checkpoint, device)
test_loss, test_acc = evaluate(model, test_loader, criterion, device)   # -> 98.62%
```

早停的意思是"**最近几轮的验证集成绩在退步**"（否则它不会触发）。所以训练结束时模型里装着的，恰恰是**那个开始退步的版本**。

- **98.80%** = 第 9 轮的模型在测试集上的成绩（验证集上它是 98.41%，比第 6 轮的 98.42% 低）
- **98.62%** = 第 6 轮的模型在测试集上的成绩

**这一轮模型在验证集上更好，在测试集上反而更差** —— 这就是第 5 章 5.5 节讲的"验证集最好 ≠ 测试集最好"，两个数字差 0.18pp，落在噪声带内。

**但工程上的问题不是谁高谁低，是"你交付的到底是哪个模型"。** 教学脚本的写法有个隐患：它一边把第 6 轮的权重存进了 `best_cnn.pt`，一边打印第 9 轮的成绩 —— 这两个数放在一起，读的人很容易以为"98.80% 就是这个 checkpoint 的水平"。而第 7 章加载 `best_cnn.pt` 实测出来的就是 **98.62%**，不是 98.80%。

工程版没有这个歧义：**checkpoint 存的是 best，评之前把它装回来，评的就是交付的那个模型。**

<blockquote class="tip">

**💡 所以第 5 章那个差值是教材，不是 bug**

本书**不改**第 5 章的写法 —— 那个 0.18pp 的差值本身就是很好的教学内容（"你以为你交付的是那个模型，其实不是"）。

工程版在这里做了正确的事，恰好也让本章和第 7 章对上了：**两边都是 98.62%，因为它们加载的是同一份权重**（8.4 节已经验证过逐元素相等）。

</blockquote>

## 8.7 怎么用到 PoolNet

本章的真正目的不是 MNIST —— 是给你一个**可以直接套的骨架**。接下来做 PoolNet（或者任何一个图像任务），照这个结构改：

| 文件 | 要改什么 | 不用改什么 |
|---|---|---|
| `config.py` | 加 PoolNet 的超参（池化方式、层数…） | 路径那一段原样照抄 |
| `model.py` | 换成 PoolNet 的网络 | `build_model` / `count_params` 的形状不变 |
| `dataset.py` | 换成你的数据集 | `get_loaders` 的三件套划分不变 |
| `engine.py` | **基本不用改** | 训练循环、评估、checkpoint 全都通用 |
| `train.py` | 可能改一行（换优化器） | 流程顺序原样 |

**变的是那三个文件，不变的是 `engine.py`。** 这个比例就是这套结构好不好的判据 —— 如果每次换任务都要重写 `engine.py`，说明当初的职责没划对。

### 三条能直接搬走的经验

**① 先用教学脚本把逻辑跑通，再重构成工程结构。**

本章的工程版不是凭空写的 —— 每段代码都能在第 1~7 章找到出处。**先让它在一个文件里跑对，再拆。** 反过来（先设计漂亮的结构再往里填逻辑）很容易设计出一个跑不通的架构。

**② 重构的验收标准是"权重逐元素相等"，不是"能跑"。**

见 8.4 节。做到这一条，你才敢说"我什么都没改变"。做不到，就当换了个新模型，重新评估。

**③ 路径只在 `config.py` 里算一次。**

见 8.2 节那个警告框。`__file__` 出现在第二个文件里，就是一个随时会以"不报错的方式"出错的隐患。

## 8.8 逐行读 `train.py`

`train.py` 只有 78 行有效代码。它值得逐段看，因为它示范了"入口该长什么样"。

### 导入：什么都不用做

```python
from config import Config
from dataset import get_loaders
from engine import evaluate, fit, get_device, load_checkpoint, set_seed
from model import build_model, count_params
```

**同目录 import，不需要任何 `sys.path` 技巧。** 脚本直接执行时，Python 会把「脚本所在目录」放进 `sys.path[0]`，所以这四行能直接找到。

两种调用方式都验证过：

```bash
python code/ch08_project/train.py          # 从仓库根 —— OK
cd code/ch08_project && python train.py    # 在自己目录里 —— 也 OK
```

<blockquote class="warn">

**⚠️ 踩到的坑：一行"看起来很专业"的废代码**

`train.py` 初版在 import 前面写了这么一行，还给配了段注释解释"为什么要加"：

```python
sys.path.insert(0, str(Path(__file__).resolve().parent))   # ← 多余的
```

**实测把那行删掉，两种调用方式都照样跑通。** 也就是说那行和它的注释**都是废的**。

这类代码比明显的 bug 更值得警惕：

- **删掉它不报错**，所以没人会去删
- **留着它也不报错**，所以没人会质疑
- 但它传达了一个**错误的心智模型** —— 让每个读代码的人都以为"同目录 import 是需要动 `sys.path` 的"，于是以后在别的地方也顺手加上一行

**遇到这种情况，选择删掉，而不是留着"以防万一"。** 真正需要动 `sys.path` 的情形是"用 `-m` 跑包"或者"从别处 import 这个脚本"——本章都不是。

</blockquote>

**注意这里没有包结构**（没有 `__init__.py`、也没有相对导入 `from .config import`）。这不是偷懒 —— 包结构是为了"被别的项目 import"，而本章的工程版是**一个直接运行的独立程序**。为它建包，只会让运行命令从 `python train.py` 变成 `python -m ch08_project.train`，徒增麻烦。

### 只声明"能改什么"，默认值不重复

```python
def parse_args() -> argparse.Namespace:
    d = Config()                                        # 先拿一份默认配置
    p = argparse.ArgumentParser(description="第 8 章：工程结构版训练入口")
    p.add_argument("--smoke", action="store_true", ...)
    p.add_argument("--epochs", type=int, default=d.epochs)
    p.add_argument("--lr", type=float, default=d.lr)
    ...
```

`parse_args` 里**不出现任何字面量默认值** —— 每个 `default=` 都指向 `Config` 的字段。所以"默认是多少"只有一处定义。

初版写的是 `default=10`、`default=0.01`，与 `Config` 里的值重复了一遍（8.3 节 ② 有详述）。**那是个不如第 5 章的写法** —— 第 5 章至少用了 `default=CANONICAL_LR` 引用常量。

多出来的 `d = Config()` 这一行值得。它同时起两个作用：

1. 消掉了默认值的第二份副本
2. **`Config()` 本身就是一份"默认配置长什么样"的文档** —— 读到这里就知道不传任何参数时会跑什么

（真正的工程做法通常是**完全不从命令行传超参**，而是读一个配置文件 —— 那样 `parse_args` 只剩 `--config` 一个参数，这类重复自然消失。见练习 1。）

### 冒烟的两条约束写在明面上

```python
if cfg.smoke:
    cfg.epochs = min(cfg.epochs, 1)
    if cfg.limit == 0:
        cfg.limit = 512
```

**要显式写在 `main` 里，不要藏进 `Config`。**

藏进去（比如在 `from_args` 里判断 `smoke` 就改 `epochs`）看着更"干净"，但读 `main` 的人就再也看不出"冒烟到底哪里变小了"，只能去翻 `Config` 的源码。

**"冒烟做了什么"是 `main` 流程的一部分，就该在 `main` 里看得见。**

### 关键的一步：装回 best 再评

```python
load_checkpoint(model, cfg.checkpoint, device)
test_loss, test_acc = evaluate(model, test_loader, criterion, device)
```

见 8.6 节。**这两行是本章最重要的一处行为差异。**

### 最后一句话不要省

```python
if best_epoch < cfg.epochs:
    print(f"  注：验证集最好在第 {best_epoch} 轮、测试集是另一个数 —— "
          f"两者不看同一批数据，本来就不该相等（第 5 章 5.5 节）。")
```

"验证集 98.42% 但测试集 98.62%，是不是代码写错了？" —— 这是这类脚本被问得最多的问题，**直接印出来**比写在文档里有用。

**一个好的入口程序，会把最容易被误解的地方主动解释掉。**

## 小结

- **前七章的 27 份副本**（`set_seed` × 8、`get_device` × 8、`evaluate` × 6、`train_one_epoch` × 5）是"每章自包含"的代价。教学值得付，工程付不起
- **五个文件的职责**：`config` 管数字、`model` 管结构、`dataset` 管数据、`engine` 管流程、`train` **只管编排**。判断标准是"换个场景它会不会变" —— `train.py` 应该是最不需要改的那个
- **依赖单向、不许有环**：`train → engine/model/dataset → config`。落地成一条可见的规矩：**`__file__` 只在 `config.py` 里出现一次**（`parent` 要三层，第 1~7 章是两层）
- **同一份逻辑，两种写法**：散装参数 vs 打包 `cfg`、默认值引用 vs 字面量、保留岔路 vs 只留结论、自建损失 vs 传入损失。**教学版保留所有岔路，工程版只保留结论**
- **但别把"工程版写法"自动当成更优**：本章的 `parse_args` 初版把默认值写成字面量，**比第 5 章的 `default=CANONICAL_LR` 还差**（两处副本）。结构化不会自动变对，具体写法仍要一条条看
- **重构的验收标准是"权重逐元素相等"**，不是"能跑"也不是"准确率差不多"。实测 `ch08_best.pt` 与第 5 章的 `best_cnn.pt` **8 个张量逐元素完全相等**
- **`ch08_best.pt` 连跑两遍 md5 逐字节相同**；唯一不可复现的是「秒」那一列
- **⚠️ 踩到的坑**：`get_device()` 里的 `torch.randn` 会**消耗全局随机数流**。先 `set_seed` 再探测设备 → 初始化拿到偏移过的随机数 → 第 1 轮 val 就从 96.68% 变成 96.76%、测试集 98.53%（不是 98.62%）。**修法：先 `get_device()` 再 `set_seed()`**
- **0.09pp 靠数字判断会被当成噪声。** 是"从第 1 轮起整条曲线就不一样"这个**形状**暴露了它 —— 对比两组结果时要并排看曲线，不只看最后一个数
- **工程版比教学版多做一件事**：评测试集**之前先把 best checkpoint 装回去**。第 5 章评的是末轮模型（98.80%），工程版评的是交付的那个模型（98.62%，与第 7 章一致）
- **换成 PoolNet**：改 `config`/`model`/`dataset` 三个文件，`engine.py` 基本不动。**这个比例就是职责划得对不对的判据**
